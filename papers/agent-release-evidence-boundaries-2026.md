# Release Evidence Boundaries for Cross-Platform, Self-Hosted AI Agents

**Shafaet Brady Hussain**
Independent researcher, ResearchForumOnline, United Kingdom
27 September 2026

## Abstract

An AI desktop release may have a passing source suite, a built installer, a live website and a model endpoint while still failing the user's real task. I present a release-evidence matrix for local and self-hosted agents using TalkToAi Code 8.0 as an author-led case study. The matrix separates source commit, tests, packaged startup, installer bytes, installed application, remote inference route, portable OS smoke, public download and interactive task outcome. The release has public Ubuntu/macOS smoke receipts and a Windows installer digest; an author-led local check recorded installation with preserved settings. These observations support distribution and specific software invariants, not general model ability. The paper proposes a reproducible release passport that records entity hashes, activity receipts, expected scope and the limits of each result.

## 1. Research question

What evidence is required to say that a self-hosted AI agent is *available*, *installed*, *connected*, or *capable*? These predicates should not collapse into “working.” A Git tag can exist without a valid installer. An installer can launch while the user's model tunnel is offline. A model can stream tokens while returning tool markup as text. A game import check can pass while gameplay is poor.

The proposed unit is a release claim linked to a specific artifact and observation. Each claim should name its subject, environment, procedure, result, timestamp, and known blind spots.

## 2. Evidence matrix

| Claim | Minimum observation | Remaining question |
| --- | --- | --- |
| Source published | Commit and tag resolve to the intended tree | Are dependencies and build steps reproducible? |
| Tests passed | Named suite, commit, environment, exit status | Are cases representative of user tasks? |
| Package starts | Packaged binary launches a bounded self-test | Does full interactive use work? |
| Installer published | Asset URL, size and SHA-256 | Is it signed, reproducible, and accepted by every OS? |
| Installed locally | Installed executable hash and persisted-data comparison | Does the user's runtime route and model work now? |
| Linux/macOS supported | Platform installer and offscreen GUI smoke on clean runners | Do interactive accessibility and desktop integrations work there? |
| Model route available | Actual endpoint response and model inventory | Can that model execute tools correctly and finish a task? |
| Task complete | Files, checks and user-facing behavior observed after final edit | Does it generalize to other tasks? |

The [evidence ledger](../sources/talktoai-code-8-evidence-ledger.md) freezes the specific TalkToAi source and release receipts. The public workflow `36328173016` passed on Ubuntu and macOS. The 8.0 release asset lists a 66,392,889-byte Windows installer with SHA-256 `b12c6011da342bee6526947037b089219c6cd45ea6397ef4c68863e1a0de7744`. An author-led Windows source run recorded 429 tests with 12 skips; the packaged self-test and local installer check were also reported. These observations have different provenance and should not be merged into one “all features tested” statement.

## 3. Provenance model

W3C PROV distinguishes entities, activities and agents. A lightweight release passport can borrow that vocabulary without claiming full standards conformance. A source commit, test log, installer, installed binary and website page are separate entities. A build, test, installation and deployment are activities. Human operator, CI runner and tool are agents. Edges such as “generated by,” “used,” and “was derived from” let reviewers ask whether an installed executable corresponds to the committed source or merely shares a version string.

For this case, the commit hash is the source anchor; the public CI run binds tests to that SHA; the release asset digest binds downloadable bytes. A local installed-binary comparison is a separate author-led observation, not a public reproducible-build proof. The website content hash is yet another entity and does not prove the installer works.

## 4. Negative evidence as a first-class record

A previous portable smoke run on commit `b5b283c` failed on Ubuntu and macOS because a test fixture changed an executable mode without saving the new baseline. Commit `e5dcf58` corrected the fixture, and the next public workflow passed on both platforms. Preserving the failed run in the history makes the claim more precise: the *current* commit passed the declared workflow; a prior commit did not. Deleting or obscuring failures would impair diagnosis and reproducibility.

The failure also illustrates a subtle distinction. A false-negative test can block a release, but a fix should restore the intended invariant, not simply disable the test. Conversely, a green workflow on a narrow smoke suite must not be described as proof of full cross-platform parity.

## 5. Proposed release-passport procedure

1. Freeze commit and dependency definitions before building.
2. Record exact source test suite, skipped cases and execution environment.
3. Build a distributable and run a self-test from the packaged binary.
4. Hash the installer and compare its published asset digest.
5. On a controlled install, record pre/post application-state hashes and installed executable hash.
6. Run platform smoke on clean Linux and macOS runners and record workflow IDs.
7. Test model availability and at least one real tool loop separately, with model ID and route disclosed.
8. Publish a matrix of passed, failed, not run and out-of-scope outcomes. A change after any check invalidates the corresponding claim until rerun.

The passport should be generated from receipts where possible, with human review of descriptions. It must not copy secrets or user data into public logs.

## 6. Limitations and conclusion

This is one product and one release, with no independent lab replication. CI runners do not reproduce diverse desktop hardware. A hash proves byte identity, not code quality or security. The evidence matrix is therefore a discipline for making narrower, more truthful claims. It helps builders and readers distinguish publication, installation, connection and task performance instead of treating a green badge as a universal answer.
